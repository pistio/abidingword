# Abiding Word — Interface languages (i18n)

> [!NOTE]
> **This is a technical record for developers.** To learn how to *use* Abiding Word, see the User Guide: **[Language](guide/08-settings-updates-backups.md#language)**. Status lines below describe the time this record was written; the current state of every version is in the [milestone table](developers.md#milestones).

**Rule:** every piece of application text a user can see or hear —
labels, headings, buttons, menus, placeholders, helper text, notices,
empty states, confirmations, tooltips, status and error messages,
`aria-label`s and other screen-reader text, enum and colour names — goes
through the translation system. No hard-coded English in components.

## Languages

| Code | Language | Shown in Settings as |
|---|---|---|
| `en` | English (source and fallback) | English |
| `de` | German | Deutsch |
| `ko` | Korean | 한국어 |
| `fr` | French | Français |
| `es` | Spanish | Español |
| `pt` | Portuguese (one neutral resource for Brazil and Portugal) | Português |

All six are left-to-right. Nothing in the layout assumes it (logical CSS
where it matters), so a right-to-left language can be added later.

## How the language is chosen

1. The user's choice in **Settings → Language**, if one was made.
2. Otherwise the system/webview language (`navigator.languages`), reduced
   to its primary subtag: `en-GB` → `en`, `de-DE` → `de`, `ko-KR` → `ko`,
   `fr-FR` → `fr`, `es-*` → `es`, `pt-BR`/`pt-PT` → `pt`.
3. Otherwise English.

The choice is a **device preference**, stored in the webview's local
storage as `abiding-word.ui.language` (`src/i18n/languages.ts`), like the
workspace layout. It is not in the SQLite database, so changing
`ABIDING_WORD_DATA_DIR`, resetting the layout or deleting studies never
changes it. Changing the language re-renders the interface at once without
remounting anything: the open study, Scripture passage, library state and
pane layout stay. `<html lang>` follows the active language.

A missing translation falls back to English; an invalid stored value is
ignored. Keys are typed against the English resources, so a misspelt or
missing key is a TypeScript error rather than raw key text in the window.

## Library and files

[i18next](https://www.i18next.com/) with
[react-i18next](https://react.i18next.com/): mature, small, with
interpolation, CLDR plural rules (`Intl.PluralRules`) and typed keys. No
language-detection plugin (the three rules above are a few lines) and no
network: all resources are bundled and loaded eagerly (they are small).

```text
src/i18n/
  index.ts         initialisation, setLanguage(), currentLanguage()
  languages.ts     supported languages, detection, persistence
  resources.ts     assembles the JSON files; English types the keys
  messages.ts      translates coded messages from the native core
  scripture.ts     bookName(), referenceLabel()
  format.ts        formatNumber(), formatDate() (Intl)
  locales/<lang>/  app, books, common, errors, library, scripture,
                   settings, studies (.json)
```

Each file is one area of the interface; its top-level key is the file
name, so `t("library.add.title")` lives in `locales/<lang>/library.json`
under `add.title`.

## Using it

```tsx
const { t } = useTranslation();
t("common.save");
t("library.search.resultCount", { count });      // plural
t("studies.relations.exists", { title });         // interpolation
```

Outside React (rare): `import i18n from "@/i18n"; i18n.t(...)`.

- **Keys** are semantic and stable: `library.add.title`,
  `studies.findings.empty`, `common.cancel` — never the English sentence.
  Shared words (`Back`, `Save`, `Cancel`, `Delete`, `Edit`, `Remove`,
  `Close`, `Show more`…) are in `common`.
- **Interpolation**: values stay out of the prose — `"Remove “{{title}}”?"`.
  Never build a sentence by concatenating translated pieces.
- **Plurals**: give the base key with i18next suffixes for each CLDR
  category the language uses (`_one`, `_other`; French, Spanish and
  Portuguese also `_many`; Korean only `_other`), and pass `count`.
- **Enums**: the database stores stable values (`observation`,
  `teaching_idea`, `pdf`, `private`, `dark`); only their labels are
  translated (`studies.findingType.observation`). Never store a label.
- **Accessibility text** is translated like any other text, including
  labels built with values (`t("app.panes.moveLeft", { pane })`).
- **Numbers and dates**: `formatNumber`, `formatDate` (Intl with the
  active language). No date library.

## Application text vs the user's content

Translated: everything Abiding Word itself says. **Not** translated: what
belongs to the user or a source — study titles and text, findings, notes,
tags, imported books and documents, Bible text, source metadata, author
names, file names, quotations, and the names a Bible file gives itself
(e.g. "World English Bible", its licence text).

### Built-in templates

The six catalogue templates and four retained legacy definitions are application
text with stable keys (including `passage-study` and section keys such as
`observations`). Their names,
descriptions, section titles and guidance are translated for display
(`studies.builtin.templates.<key>`). The database keeps the English they
were installed with and nothing stored is rewritten.

When a study is created, its sections are **copied** and become the
user's own content. A copied section is shown translated only while it
still has exactly the built-in key and English wording; once the user
renames it, their wording is shown as written (`builtinText.ts`). The same
holds for the "Notes" section of a study without a template. "Duplicate
and customise" makes the user's own copy in the current interface
language. User-made templates are shown as written.

Structured parts keep their field definitions and translation source in a
per-study snapshot. Labels, help, choices and optional examples use that source;
missing translations fall back to English, then saved text for unknown keys.
Plain section titles and guidance use the known template key when available to
avoid collisions (for example French “Application” versus “Mise en pratique”).
Optional built-in parts retain their canonical text so they still translate
after changing language. Custom headings and guidance stay as written.
The pt folder contains Brazilian Portuguese and accepts the system tag pt-BR.
POZETEK is displayed as a method name only in German; the other five languages
use descriptive names.

### Bible book names

Canonical references (`JHN.15.7`), storage and the reference parser are
unchanged. Book names and passage labels are translated for display
(`books.json`, `referenceLabel()`): the interface may show *Johannes 15,7*,
*요한복음 15:7*, *Jean 15:7*, *Juan 15:7* or *João 15:7*. The parser still
accepts only its documented English forms (*John 15:7*, *Jn 15:7*,
*Rom 8:1-17*); typed references in other languages are future work (a
parser alias dictionary per language, docs/scripture-v0.2.md).

## Messages from the native core

The Rust core does not choose a language. An error payload is
`{ kind, message, code?, params? }`: `code` is a stable message key
(`library.passwordProtected`) and `params` its values (`{ fileName }`);
`message` is the English text, used for the log and as the fallback.
`toApiError()` turns it into the interface language through
`errors.<code>` (`src/i18n/messages.ts`); kinds whose wording never varies
(`database`, `filesystem`, `notFound`, `migration`, `integrity`, `backup`,
`unexpected`) are translated from the kind. Bible import issues and the
library's "cannot import" reason carry codes the same way. A `bookCode`
parameter is shown as the book's name in the interface language.

Developer logs, technical details and stack traces stay English.

## Terminology

French *vous*; Spanish *tú* and Portuguese *você* (modern software usage);
Korean polite *-하세요/-합니다* in sentences, short nouns on buttons. Never
assume the user's gender.

Notes: German uses *Bibelstudium* for the generic study object and activity, while
specific analytical study types use compounds such as *Bibelstellenstudium*,
*Wortstudium* and *Themenstudium*. *Bibelstelle* is a reference range;
A study's sections are *Teile* (v0.17; before, *Abschnitt*, which also means a
passage of the Bible). A generic Finding is a *Notiz* (v0.17; before, *Eintrag*),
because it may be a question, quotation, unresolved issue, application, or
conclusion and is not necessarily an *Erkenntnis*; where possible no generic
noun is shown at all, only the kind (*Beobachtung*, *Frage*…). *Lehre* remains the term for Doctrine;
teaching/sermon preparation is *Lehr- / Predigtvorbereitung*.

In Korean, the generic user-facing Study is *성경공부*. *연구* is **not** the
generic translation of Study: it reads as academic research and is kept only
for genuinely scholarly contexts. Study types are *본문 공부*, *단어 공부*,
*주제별 성경공부*, *성경신학* and *조직신학* (no *연구*). A Project is a
*성경공부 모음* (*모음* where short; the intro names sermon series, Bible-study
courses, a single Bible book or a doctrine as examples). A Template is a
*공부 틀* / *성경공부 틀*; "no template" is *빈 성경공부*. A Section is *부분*
(not *단락*, which is a prose paragraph). The English/code word "block" never
appears in the Korean UI: use phrasing such as *이 {{type}}을(를) 삭제할까요?*.
The former Note block is *참고*; a Scripture note is *메모*. Do not use the
transliterations *프로젝트*, *템플릿*, *섹션* or *블록* in the UI.
Internal domain names (Project, Template, Section, StudyBlock) remain in code
and storage; only the user-facing Korean copy changed, never database values.
The regression test `tests/ui/korean-terminology.test.ts` checks these terms
by semantic key, not by a global string ban.
Korean typography comes from v0.9: a Korean-first UI font stack and a heavier
interface weight (`:root:lang(ko)` in `src/design-system/index.css`, checked by
`tests/ui/korean-typography.test.ts`); Latin typography is unchanged. It is not
duplicated anywhere. v0.9's passage-aware Korean strings use the same terms
(*{{passage}}에 관한 부분*, *이 자료에 {{count}}곳 더 있음*).
A generic Finding is *기록*, not *발견*.
The Library is *자료실*. *자료* is used for a source/resource in the Sources
pane, while *출처* is used for citation/provenance. *본문* is the usual
Bible-study word for the passage studied. Highlight is *강조* in visible UI.
In French, the generic Finding is *note* (v0.17; before, *élément d’étude*,
which read awkwardly and was hard to inflect): feminine, so *la note
({{type}})*. A study's section is a *partie*; a text block is *texte*, never
*bloc*.
*Citation* is a quotation and *Référence* a citation of a source. Avoid
*constat* as the generic category because it implies a conclusion already
reached.

In Spanish, the generic Finding is *apunte* (unchanged in v0.17); a study's
section is a *parte*, a text block *texto* (not *bloque*). This fits a study workspace and
can naturally contain an observation, question, quotation, application or
conclusion; avoid *hallazgo*, which suggests a discovery.

In Portuguese, the generic Finding is *anotação* (v0.17; before, *registro*,
which also means a log); a study's section is a *parte*. Avoid *achado*, which
suggests something discovered or found. Use the Brazilian-neutral *seção*,
*projeto*, *ação* spellings consistently.

Sentences that insert a type name (finding or block type) avoid articles that
would have to agree with it where practical.

## Adding a string

1. Add the English text under a semantic key in `locales/en/<area>.json`.
2. Add the same key, translated, to the other five languages.
3. Use `t("<area>.<key>")` in the component.
4. `npm run i18n:check`.

## Adding a language

Add its code and native name to `LANGUAGES` (`languages.ts`), a folder
`locales/<code>/` with every area file, and the code to `resources.ts`;
`npm run i18n:check` lists anything missing.

## Checks

`npm run i18n:check` (also run by CI, *Frontend* job):

- every locale file is valid JSON and has exactly the English keys
  (plural forms per the language's CLDR categories), no extra keys;
- the same `{{placeholders}}` as English;
- no hard-coded interface text in components: JSX text, and string
  values of `aria-label`, `title`, `placeholder`, `alt` and `label`
  attributes, must come from `t()`. A line that really holds no
  interface text (e.g. a symbol) can be marked `// i18n-ignore`.

What it cannot see — text assembled in plain TypeScript and later shown —
is a review responsibility: such text belongs in the locale files too.

### Study workspace terms (v0.10)

*Remark* (the former Note text block; stored kind `note`) is deliberately not the
word for a Scripture note or for a finding: Bemerkung, 참고, Remarque, Comentario,
Comentário. The study's own notes area was *Study notes* until v0.17, when it moved to the
end of the study as *Other notes* (Weitere Notizen, 기타 기록, Autres notes,
Otros apuntes, Outras anotações). The default
project is "My studies" (Meine Bibelstudien, 내 성경공부, Mes études, Mis estudios,
Meus estudos); the pane that starts on it is "Studies" (Bibelstudien, 성경공부,
Études, Estudios, Estudos). The Korean choices *노트* (default section), *참고*
(Remark), *공부 틀* (Template) and *모음* (short for *성경공부 모음*) were accepted
in the v0.10 Windows acceptance.
