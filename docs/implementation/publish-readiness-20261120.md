## Evidence and status rules

The five classifications are deliberately separate:

- **Implemented and verified:** the identified automated or narrowly owner-observed behaviour has evidence. This does not certify all native routes or a complete public release.
- **Implemented but Windows-unaccepted:** production code and tests exist, but the current combined binary still needs the specified native observations.
- **Genuinely incomplete:** an identified engineering requirement is absent or unsafe; it is not an old issue description of functionality that now exists.
- **Blocked by external decisions:** the owner or another authorised reviewer must resolve a rights, product, independent-evaluation or distribution decision.
- **Deferred beyond initial publication:** a wider product direction that is not required for an honestly scoped initial release.

**Final recovery verification:** `RECOVERY_VERIFICATION_PENDING`. The authoritative command results, counts, exact implementation SHA and CI run IDs belong in [the verification record](daily-recovery-20261120-verification.json). Until that record is complete, the new recovery changes are not reported as fully green.

The starting CI [run 44825652838](https://github.com/pistio/abidingword/actions/runs/44825652838) is retained as a failure: the Rust job passed; the frontend reported 1,389 passing tests in 129 files but failed on an unhandled `Invented save failure` rejection. Passing assertions did not make that run successful. The milestone must resolve both rejection timing and the underlying save/restore race guarantees, then run the complete suites at the final implementation commit.
